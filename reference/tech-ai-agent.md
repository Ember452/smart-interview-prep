## 1. Agent 架构与范式

### 1.1 Agent 核心概念与边界

- **Agent 是什么？** — Agent = LLM + Planning + Memory + Tools。能感知环境、决策并执行动作的自主系统。Agent Loop 本质是 while 循环：推理 → 工具调用 → 上下文更新 → 重复，直至任务终止
- **Agent vs Chatbot 的本质区别？** — Chatbot 是单轮问答/有限多轮；Agent 具备目标驱动的规划循环、工具调用、记忆与自主决策。**追问变体（面经实证）**：「如果 Chatbot 挂了工具调用，它还只是 Chatbot 吗？」——工具调用是必要条件之一，但仅挂工具无规划闭环仍不算 Agent；判据是「是否围绕目标自主决策并循环执行」
- **Agent vs Workflow vs 传统编程？** — 传统编程和 Workflow 是人在设计期做决策，Agent 是运行时 LLM 做决策。Workflow 确定性高、可测、成本低；Agent 灵活但不可控面大。工程实践是**混合**：确定性节点用 Workflow，开放决策节点交给 LLM
- **Agent 能力天花板：模型能力还是 Harness 复杂度决定？** — 双因素：模型决定单步推理上限，Harness（上下文管理/工具/编排）决定系统级能力。工程化能把小模型撑到可用，但涌现级能力仍依赖模型。复杂度推到临界点是否出现不可控涌现——无定论，需通过评测与护栏控制（面经实证：阿里二面原题）

### 1.2 推理范式

- **ReAct 执行链路？** — Thought（推理该做什么）→ Action（调用工具）→ Observation（观察结果）→ 循环 → Final Answer。关键：每一步推理都基于上一步观察，可解释、可审计
- **ReAct vs 固定 Workflow？** — ReAct 动态决策适应开放场景；固定 Workflow 确定性流程（审批、固定流水线）更稳更省。**选型判据**：流程是否稳定可枚举；失败成本是否可承受；是否需要中间人工节点
- **ReAct vs Plan-and-Execute？** — Plan-and-Execute 先制定全局计划再逐节点执行；ReAct 边做边想。**长链路任务为什么 Plan-and-Execute 更稳定（面经实证）**：全局计划减少中间决策漂移、单次规划省 token、执行节点可独立验证与重试、可审计
- **Re-planning 触发条件怎么设（面经实证）？** — Observation 与计划假设严重不符、执行连续失败 N 次、新增约束/目标变化、关键依赖缺失。触发后更新剩余计划而非全盘重来
- **Reflection 反思模式？** — Reflexion（失败后反思再试）、Self-Refine（生成后自我批评改进）、CRITIC（外部工具验证）。注意：反思结果不要直接污染下一轮上下文，应隔离存储

### 1.3 Agent 框架选型

- **LangGraph vs LangChain？** — LangChain 是链式抽象（Linear Chain），适合固定流程；LangGraph 是图编排（State/Node/Edge），支持循环、分支、条件边，适合 Agent 循环
- **LangGraph 的 State/Node/Edge 分别解决什么问题（面经实证）？** — State：跨节点共享的全局状态（对话历史、任务进度），解决上下文漂移；Node：原子执行单元（LLM 调用/工具执行/判断）；Edge：控制流（顺序/条件/循环），决定图拓扑
- **为什么选 LangGraph 而不是 AutoGen、CrewAI 或手写状态机？** — AutoGen：多 Agent 对话式协作，调试困难；CrewAI：角色化团队抽象，灵活度低；手写状态机：完全可控但状态管理、持久化、可视化成本高。LangGraph 平衡：显式图 + 状态持久化 + 检查点 + 可视化调试
- **框架能力不满足时怎么扩展（面经实证）？** — 自定义 Node 包装任意代码；Custom State Reducer 控制状态合并；Checkpointer 接入外部存储；不满足时降级为手写状态机并保留可观测性
- **扣子等低代码平台怎么看（面经实证）？** — 优势：快速搭建、非技术可用、内置插件生态；局限：编排能力受限（复杂分支/循环）、调试与灰度困难、深度定制难、平台锁定。选型：原型验证/业务快速落地用低代码，深度 Agent 工程用代码框架

### 1.4 GraphRAG 与多跳推理

- **为什么选 GraphRAG？和纯向量检索的区别（面经实证）？** — 向量检索做语义相似召回，处理"相似文本"问题；GraphRAG 建立实体关系图，处理**多跳关系推理**与**聚合性问题**（如"哪些项目用了 Redis 并遇到主从延迟"）。代价：构建成本高、维护复杂
- **什么算推理型问题（面经实证）？** — 需要多步关联（A→B→C）、跨文档聚合统计、对比/因果/路径类问题。单点事实查询（"Redis 默认端口"）不算

### 1.5 Agentic RAG

- **Agentic RAG 与传统 RAG 的区别（面经实证）？** — 传统 RAG：一次检索一次生成，检索是固定管线；Agentic RAG：Agent 自主决策"是否需要检索、检索什么、检索失败怎么办、要不要多轮检索"，检索成为工具
- **Query Rewrite 是否算 Agentic？** — 是轻量级 Agentic 特征（决策 + 行动），但完整 Agentic 还需检索评估与策略调整
- **多轮检索如何设计？** — 首轮检索 → 评估答案完整性/置信度 → 不满足则改写 Query 或换检索路再查 → 终止条件：答案完整或达到最大轮次
- **检索失败后 Agent 怎么调整（面经实证）？** — 扩召回（放宽 Top-K/换路）、Query 改写、换知识源、声明无法回答、转人工
- **Agentic RAG 的成本和稳定性怎么控制？** — 限制最大检索轮次、低置信度直接回退传统 RAG、缓存、评测兜底

### 1.6 上下文工程

- **Context Engineering？** — 为 LLM 构建高信噪比信息输入环境：结构化 System Prompt、工具描述精简、历史摘要化、关键信息（约束/任务）绝对保护
- **State 如何应对长对话带来的上下文漂移（面经实证）？** — 关键状态外置到 State（非自然语言历史）、每轮显式更新、恢复时重建上下文而非全量回放
- **上下文窗口溢出怎么办？** — 滑动窗口 + 摘要压缩早期对话；RAG 检索相关片段替代完整历史；分层记忆（见第 3 章）；Prompt Cache 降成本

### 1.7 多 Agent 架构范式

- **主流范式？** — Orchestrator-Subagent（编排者分派任务、汇总结果，防扯皮）；Peer-to-Peer（对等协作，灵活但易冲突）。生产多用前者
- **如何避免多个 Agent 相互扯皮或死循环（面经实证）？** — 明确角色边界与职责清单；消息带超时与最大轮次；集中仲裁（Orchestrator 有最终裁决权）；终止条件显式声明；共享状态而非对话式协商
- **子代理（Sub-agent）机制？** — 独立上下文执行隔离任务，避免污染主上下文；可并行；完成后只返回结论

## 2. Tool Calling 工程

### 2.1 设计

- **Tool 输入输出 schema 怎么定义（面经实证）？** — JSON Schema 严格类型；**描述写清"何时该调用、何时不该调用"**；参数含格式要求与示例值；输出结构化便于程序消费。Tool 描述是模型选工具的说明书，质量直接决定调用准确率
- **Tool 是直接暴露给模型，还是通过服务端做分发（面经实证）？** — 服务端分发更优：模型只面向"工具目录"，服务端做参数校验、权限校验、限流、审计、灰度。直接暴露的隐患：模型可能传非法参数、越权调用、被 Prompt Injection 诱导
- **工具规模暴增（几百个）怎么设计发现机制防 Context 溢出（面经实证）？** — 分层：高频工具常驻描述、长尾工具按命名空间/语义索引按需检索注入；工具描述压缩（一句话 + 详情页）；分类路由（先选类再选工具）

### 2.2 容错

- **工具调用失败怎么处理（面经实证）？** — 分类处理：网络错误 → 指数退避重试；业务错误 → 错误信息返回给模型二次决策；结构性失败 → 降级到 fallback 工具/人工程序。**禁止无限重试**
- **工具参数错误怎么兜底（面经实证）？** — 服务端 schema 校验 → 自动纠正（可枚举错误如枚举值越界）→ 纠错失败把校验错误返回模型重新生成参数 → 仍失败则拒绝调用并反馈
- **Agent 调外部 API 超时或异常，容错和自我修复逻辑怎么设计（面经实证）？** — 超时分级（快速失败 + 慢超时）；熔断（连续失败开闸）；幂等键防重复；状态机记录每步状态支持断点恢复；重试队列 + 人工兜底
- **如何防止模型调用危险工具（面经实证）？** — 权限分级（只读/写/高危）；高危操作人工审批或二次确认；沙箱执行；工具白名单；输入校验与 Prompt Injection 防护（外部输入与系统指令隔离）

### 2.3 诊断

- **如何判断是 Prompt 问题还是模型能力问题（面经实证）？** — 控制变量：同一任务换更强模型（能力问题则强模型改善）；同一模型简化/改写 Prompt（Prompt 问题则改善）；工具对比（描述质量差异）；bad case 归因表（输入/上下文/指令/能力四象限）
- **Function Calling 的明显局限（面经实证）？** — 依赖模型原生支持；参数幻觉（编造不存在的参数值）；多函数顺序依赖难表达；工具描述越长 token 开销越大、注意力稀释；对动态 schema 支持弱
- **怎么改进（面经实证）？** — 语义路由 + 小模型选路；few-shot 调用示例；结构化输出约束；工具分组嵌套；服务端兜底校验

## 3. 记忆与上下文

### 3.1 记忆分层

- **为什么要分层记忆（面经实证）？** — 不同信息的更新频率、生命周期、召回方式不同：工作记忆（当前会话，全量保留最近 N 轮）→ 短期记忆（会话摘要）→ 长期记忆（跨会话，用户画像/项目知识）。单层记忆要么溢出要么丢失
- **静态长期记忆 vs 动态长期记忆（面经实证）？** — 静态：用户声明性信息（身份、偏好、约束），低频更新、高权威；动态：行为积累（使用习惯、历史任务），持续写入、需聚合去噪。**为什么分离**：更新策略不同（静态人工确认、动态自动聚合）、召回优先级不同（静态优先）、过期处理不同
- **项目级规则、用户偏好、会话上下文怎么隔离（面经实证）？** — 三级隔离：项目级 Rules（团队共享、加载优先级最高）、用户级偏好（个人、可覆盖项目级？需定义优先级）、会话上下文（临时）。隔离手段：分文件存储 + 加载优先级 + 命名空间
- **上下文过长时性能下降怎么处理（面经实证）？** — 压缩 + 检索 + 缓存三件套；长上下文模型（如 200k）也应按需注入而非全塞；注意"Lost in the Middle"（关键信息放开头/结尾）

### 3.2 记忆控量与召回

- **长期记忆快速积累、存得过多怎么控量（面经实证）？** — 触发限流（不是每轮都写，如会话结束才沉淀）；重要性评分 + 阈值；同主题合并去重；TTL 过期；容量上限 + 淘汰策略（LRU/按价值）
- **大模型怎么决定长期记忆是否召回（面经实证）？** — 显式触发（用户提及）→ 语义相似度检索（Embedding）→ 意图识别（规划时判断是否需要历史）→ 混合阈值。召回结果注入前要标注来源与时间，防过期信息误导

### 3.3 上下文压缩

- **压缩阈值怎么设定（面经实证）？** — 依据：上下文窗口大小 × 安全系数（如 200k 窗口设 150k 阈值，为输出与工具结果留余量）；实测 token 增长速率（每轮 ~Xk，估算可用轮数）；触发上限要有依据而非拍脑袋——面试官会追问"为什么选这个值"
- **如何避免摘要丢失关键信息（面经实证）？** — 结构化摘要模板：关键实体、用户约束、未完成事项、决策记录、技术细节分字段保留；分层摘要（逐轮摘要 + 全局摘要）；摘要对象排除 System Prompt 与工具定义；压缩后可用"摘要重建测试"验证关键信息可恢复
- **对话压缩如何控制折损率（面经实证）？** — 评测：压缩前后回答一致性（对同一问题集合对比）；保留最近 N 轮原始对话 + 早期摘要；按信息类型分级保留（决策 > 过程）；折损超过阈值回退到更大窗口模型
- **滑动窗口 + 历史摘要具体逻辑？** — 保留最近 N 轮完整对话（面经实证常见 N=3，依据：多数问题只需近 3 轮上下文），更早的压缩为摘要；摘要追加到上下文头部

## 4. 多 Agent 协作

- **多 Agent 通信，协议层面怎么优化省 Token（面经实证）？** — 结构化消息（JSON 字段：类型/目标/负载/元数据）替代纯自然语言；只传结论不传过程；压缩引用（传 ID 不传全文）；共享黑板（Blackboard）模式避免重复广播
- **任务分配和结果汇总怎么设计，防互相甩锅或重复劳动（面经实证）？** — 任务注册表（谁领了哪个任务，原子认领）；结果校验（接收方验证而非信任）；重复检测（任务哈希）；Orchestrator 汇总时带责任记录
- **如何避免死循环/互相扯皮（面经实证）？** — 最大消息轮次硬限制；超时终止；角色边界不可越权；争议升级机制（提交仲裁者/人类）；共享状态机替代对话协商
- **如何区分"有效推理"和"原地兜圈子"（面经实证）？** — 信号：状态是否推进（工具调用是否有新信息）、步骤是否重复（动作哈希）、路径是否收敛；量化：每步有效性打分、目标距离估计（见第 6 章）

## 5. RAG 深度

### 5.1 检索质量

- **为什么要加 Rerank（面经实证）？** — 向量粗召回（Bi-Encoder 快但精度低）→ Cross-Encoder 精排（慢但准）。两阶段在精度/时延间取平衡
- **Recall@K 和 Precision@K 怎么取舍（面经实证）？** — Recall 看"该召回的召回了没"（K 大 → 高召回低精度）；Precision 看"召回的准不准"（K 小 → 高精度低召回）。取舍依据：生成侧对噪声的容忍度、上下文预算；Rerank 后可用大 K 召回 + 精排保证两者
- **Top-K 怎么动态调整（面经实证）？** — 按 query 类型（事实查询 K 小、综述 K 大）、按首轮召回置信度、按上下文预算动态分配
- **BM25 已经很好，向量检索还有必要吗（面经实证）？** — 有：同义改写、语义匹配、跨语言、口语化 query 是 BM25 盲区；BM25 擅长精确词与专业术语。**混合检索**（RRF/加权融合）通常最优；数据量小时 BM25 可能已够用，避免过度设计
- **混合检索权重怎么调优，冷启动初始权重怎么给（面经实证）？** — RRF 无权重；加权融合冷启动给 50/50 或按数据量（术语密集域关键词权重大），有评测集后按 Recall@K 网格搜索调优

### 5.2 分片策略

- **语义分片怎么切才不切断知识连贯意图（面经实证）？** — 段落/标题感知分片优先；Embedding 边界检测；重叠区（10-20%）保连贯；表格/列表整体成片不切割
- **多模态文档，文字和图表的切片粒度怎么对齐（面经实证）？** — 按版面（Layout）划分视觉块，图表与引用它的文字段落绑定为一个语义单元；跨页表格利用 Layout 信息重建结构不割裂（面经实证：MinerU 场景）

### 5.3 索引

- **常用向量索引算法？时延与精度怎么权衡（面经实证）？** — FLAT（暴力，精确慢）、IVF（倒排聚类，快但有召回损失）、HNSW（图索引，高召回低延迟，内存贵）、PQ（量化压缩，省内存损精度）。权衡维度：数据量/召回要求/时延预算/内存成本
- **索引需要增量更新怎么设计（面经实证）？** — 新数据批量写入临时段 → 定期合并（segment merge）；删除用墓碑标记；避免逐条更新 HNSW 图（性能差）

### 5.4 冲突与失败

- **RAG 拉回的文档观点互相打架，怎么缓解防模型被带偏（面经实证）？** — 冲突检测（相似度聚类找矛盾对）→ 按来源权威性/时效性加权 → 提示词要求模型呈现分歧并说明依据 → 引用溯源；无法裁决时输出"存在不同观点"
- **检索结果含干扰信息怎么降噪（面经实证）？** — 混合检索权重调优、相关性阈值过滤、Rerank、Query 改写收敛意图、上下文重排（相关信息置前）

## 6. 评测方法论

### 6.1 评测体系

- **迭代调整 RAG/Prompt/架构时，怎么验证 Agent 效果、确认优化优于旧版本（面经实证）？** — 固定评测集（覆盖典型场景 + bad case 回归集）→ 新旧版本同集对比 → 量化指标（正确率/检索指标/用户反馈代理指标）→ 消融实验定位提升来源 → 统计显著性（样本够时）。**"体感提升了"不算数**
- **Agent 系统设置哪些性能/稳定性指标（面经实证）？** — 回复时长（P50/P95）、API 调用错误率、工具调用成功率、任务完成率、上下文利用率、成本/请求、可用性
- **对 Agent 推理轨迹，怎么用中间节点的有效性量化模型表现（面经实证）？** — 每步节点打标签（有效行动/无效重复/偏离目标）；指标：有效行动占比、收敛步数、无用工具调用数；"原地兜圈子"信号：动作序列重复、无新观察、目标距离无变化

### 6.2 检索与生成评测

- **检索指标？** — Recall@K（前 K 含相关文档比例）、Precision@K、MRR（首个相关文档位置）、NDCG（带排序质量）
- **RAG 生成评测？** — RAGAS：faithfulness（忠实于检索内容）、answer relevance（回答相关性）、context relevance（上下文相关性）；人工评估抽样
- **Agent 整体评测？** — 任务完成率、成功率、工具使用正确率、步数效率、成本；复杂任务用 LLM as Judge + 人工抽查双轨

### 6.3 LLM as Judge

- **LLM as Judge 怎么保证打分准确（面经实证）？** — 金标准校准（人工标注样本对 judge 打分做一致性检验，如 Cohen's Kappa）；多模型投票；rubric 明确打分标准；防 bias：位置 bias（答案顺序打乱）、长度 bias（长答案倾向高分）、自赞 bias（judge 与生成模型同源时）；抽样人工复核兜底

### 6.4 bad case 闭环

- **模型不听指令/出错的完整处理流程（面经实证四步闭环）？** — ① bad case 收集（线上日志/评测集失败项，写明输入/期望/实际）→ ② 定位（Prompt 问题/上下文问题/模型能力问题/工具问题，控制变量法）→ ③ 解决（Prompt 改写 / 参数调整 / 后处理校验 / 流程约束兜底）→ ④ 验证（回归测试 + 评测数据证明有效，防止修一个坏十个）
- **反思结果会不会污染上下文（面经实证）？** — 会。反思/失败记录应隔离存储（单独 memory 区域），只在规划阶段按需注入，不在每轮对话历史中回放

## 7. 成本控制

- **token 计费模型？** — 输入与输出单价不同（输出通常 3-5 倍于输入）；按百万 token 计价（如 $X/M input、$Y/M output）；长上下文模型单价更高
- **怎么估算成本（面经实证：写一千行代码需要多少 token）？** — 代码生成：上下文（工程信息 + 历史）远大于输出；粗估：千行代码输出 ~10-20k token，输入上下文可能 10 倍；成本 = (输入 token × 输入单价 + 输出 token × 输出单价) × 调用次数
- **为什么 Agent 成本高（面经实证）？** — Agent Loop 每步都调 LLM；上下文随历史增长；工具结果回灌；多 Agent 各自调用。放大倍数 = 循环步数
- **省钱手段？** — Prompt Cache（稳定前缀复用 KV，TTL 内命中）；历史压缩；小模型路由（简单任务用小模型）；工具描述精简；限制最大步数与检索轮次；批量与缓存

## 8. LLM 训练

- **SFT、RLHF、DPO、GRPO 区别（面经实证）？** — SFT：监督微调（模仿高质量答案）；RLHF：训练奖励模型 + PPO 强化学习（复杂、不稳定）；DPO：直接用偏好对数据优化，无需奖励模型（简单稳定，成为主流）；GRPO：DeepSeek 提出的组相对策略优化（无 Critic 模型，按组内相对优势更新，训练成本低、数学/推理任务效果好）
- **为什么 SFT 后还需要偏好优化（面经实证）？** — SFT 只学"说什么"，不学"什么更好"；偏好优化对齐人类偏好（有用/无害/风格），提升指令遵循与拒绝能力；SFT 数据是单答案监督，偏好数据是成对比较，信息量更高
- **LoRA？** — 冻结原权重，只训低秩分解矩阵（r=8-64），参数量减少 90%+；适合领域适配与风格调整；全参数微调才能学新知识/新语言
- **微调 vs RAG？** — 微调：固定模式、风格、格式遵循；RAG：动态知识、可溯源；知识型问题优先 RAG，行为型问题优先微调
- **数据集与评测？** — 规模：SFT 常用万-十万级高质量样本（质量 > 数量）；评测指标按任务（代码 HumanEval、数学 GSM8K、通用 MMLU、对话 MT-Bench、中文 C-Eval）；注意数据污染

## 9. AI 辅助开发

### 9.1 实操流程

- **AI 编程的完整流程（面经实证）？** — 需求拆解（人）→ 规则/上下文准备（Rules、相关文件）→ 分步生成（小步提交）→ 测试验证（单测/运行）→ Code Review 兜底 → 复盘沉淀
- **怎么保证 AI 生成代码质量（面经实证）？** — 规则文件（风格/约束/禁止行为）；测试先行（先生成测试再实现）；生成后强制运行验证；人工 Review 关键逻辑；小步迭代不要一次生成大模块
- **Claude Code 实操技巧（面经实证）？** — 先规划再创建 worktree（隔离变更）；Rules 分级加载；子代理处理隔离任务；checkpoint/回滚；context 管理（长任务定期 summarize）
- **大量 Rules 会不会造成上下文溢出（面经实证）？** — 会。解决：按需加载（glob 匹配/目录级）、索引化（总索引 + 详情文件）、压缩描述；了解上下文窗口大小并按预算分配
- **用过 Skill 吗？Skill 和普通 Prompt 规则最大区别（面经实证）？** — Skill 是结构化能力封装：frontmatter 元数据（触发条件/参数）、按需加载、可复用可分发、版本管理；普通 Prompt 是一次性指令，无触发机制、无法沉淀复用。Skill 是"资产"，Prompt 是"消耗品"

### 9.2 工程闭环

- **让 Agent 先写代码再做 Code Review，单 Agent 和多 Agent 谁更适合（面经实证）？** — 单 Agent：自写自审有同源偏差，但省成本省上下文；多 Agent：写码 Agent + 审查 Agent 分离，审查视角独立（能发现逻辑/安全/边界问题），适合关键模块；成本约翻倍
- **Vibe Coding 提升代码质量，怎么评估结果可靠（面经实证）？** — 测试闭环（自动化测试通过率）、运行验证（实际跑通场景）、人工抽查（关键路径 review）、评审指标（bug 密度、返工率）；"看起来对"不可靠
- **代码 Agent 落地研发流程，最关键的工程闭环是什么（面经实证）？** — 可验证性闭环：需求 → 规划（worktree）→ 实现 → 测试 → CI 门禁 → Review → 回滚预案；缺任一环 AI 代码都不可信
- **Agent 要求先规划再创建 worktree，但直接编辑代码了，如何让下一轮纠正（面经实证）？** — 流程守卫（工具层拦截越序操作）；失败信息回喂（"违反了先规划约束，请先输出计划"）；恢复机制（git 回滚到规划点重来）

## 10. 行业认知题

> 二面/三面高频（面经实证）。这类题无标准答案，考察视野与思辨。评估要点：有明确立场、有论证链条、有工程/业务视角、承认不确定性。

- **随着基模快速迭代，Agent 还有必要么？** — 要点：基模变强提升单步能力，但工具使用、多步规划、系统集成（业务系统/权限/数据）仍需 Agent 层；基模迭代反而降低 Agent 成本、扩大适用面；观点：Agent 是基模能力的"放大器与执行器"
- **未来软件是统一聊天窗口，还是保留传统 GUI？底层划分原则是什么？** — 要点：按任务确定性划分——确定性高频操作（表格、画布）保留 GUI；开放性/生成性任务（内容生成、分析、编排）走对话；底层原则：输出结构可控性与用户掌控感
- **AI 对业务最大的赋能点在哪？** — 要点：把非结构化信息处理成本打下来（客服/文档/数据解读）；个人生产力放大；业务侧要选"高频 + 成本敏感 + 可评测"的场景切入
- **你平时关注哪些 AI 相关产品、方向？** — 考察持续学习：模型（GPT/Claude/Gemini/DeepSeek）、Agent 产品（Claude Code/Cursor/Manus/扣子）、框架（LangGraph/CrewAI）、研究（多模态/推理时计算）；能说清"为什么关注、和自己的实践有什么关系"加分
- **低代码 Agent 平台和代码框架怎么选？** — 见 1.3；补充：团队能力结构（有没有 LLM 工程师）、迭代速度要求、定制深度

## 面试官追问链（通用，按回答质量动态下钻）

1. **名词抓取**：候选人抛出技术名词（LangGraph/GraphRAG/Rerank/DPO 等）→ 立即追问"具体怎么用的？原理是什么？"
2. **选型逼问**：为什么用 X 不用 Y → 评估维度 → 场景变化是否改选
3. **量化逼问**：有没有评测 → 指标多少 → 怎么测的 → 基线对比 → 预防体系
4. **bad case 闭环**：遇到什么问题 → 具体 bad case → 怎么定位 → 怎么解决 → 评测数据证明
5. **挑战式质疑**：这个方案在 X 场景下会不会有问题？（如"BM25 已经很好，向量还有必要吗"）
6. **边界异常**：超时/重试/失败/并发上限/工具循环怎么办
7. **成本追问**：这个方案 token 成本多少？为什么这么高？怎么降？
