# 面试流程展开版

本文件只保留 `SKILL.md` 中流程与出题策略的展开说明，用于维护和查阅；执行时以 `SKILL.md` 为准。

## 面试轮次模型（round_type）

真实大厂是**多轮次、各有侧重**的（技术一面→二面→三面/交叉面→总监面→HR 面），而非单场混合。
`round_type` 参数用于聚焦当前模拟的是哪一轮，不同轮次的出题重心、难度与通过门槛不同：

| round_type | 对应轮次 | 主考重心 | 难度/门槛 | 阶段权重调整 |
|-----------|---------|---------|----------|------------|
| `tech_1` | 技术一面（基础关） | 基础八股 + 手撕算法 + 项目概览 | 通过率约 40%，卡基本功 | 技术考察↑、编码↑、系统设计↓ |
| `tech_2` | 技术二面（项目关） | 项目深挖 + 场景/系统设计 | 深挖真实性与技术判断 | 项目深挖↑、系统设计↑ |
| `tech_3` | 技术三面 / 交叉面 | 架构深度 + 技术广度 + 影响力 | 高，考技术视野与 trade-off | 系统设计↑、行为↑ |
| `cross` | 交叉面（跨团队面试官） | 跨领域基础 + 通用能力 + 沟通 | 中，防团队"抱团放水" | 通用基础↑、行为↑ |
| `hr` | 总监/HR 面 | 动机、稳定性、价值观、影响力、薪资 | 非技术，考文化匹配 | 行为/软素质↑、技术↓ |
| `full`（默认） | 综合单场 | 破冰→项目→设计→技术→行为→编码→反问全流程 | 综合 | 按标准阶段分配 |

**执行规则**：
- 未指定 `round_type` 时默认 `full`（保持原有单场全流程行为，向后兼容）
- 指定具体轮次时，按上表调整阶段权重与出题重心；开场白可点明"这是技术 X 面，本轮重点考察 …"
- `hr` 轮不深挖技术，主要走 `reference/behavioral-questions.md` 的动机/稳定性题，保持轻量
- 报告中注明本轮 `round_type`，「录用建议」结合该轮定位给出"是否可进入下一轮"

## 出题原则

### 优先级

1. **项目深挖**：优先围绕简历中真实项目追问设计决策、难点、取舍、结果
2. **技术栈核心概念**：围绕简历中写到的技术，优先问高频原理与工程实践
3. **行为面试**：根据经历考察沟通、推动、冲突处理、复盘能力（STAR 追问见 `reference/behavioral-questions.md`）
4. **系统设计**：仅当年限、岗位或项目深度明显支持时提高占比

### 八股 ↔ 项目动态切换策略

真实大厂面试遵循一条隐性规则：**先深挖项目，项目撑得住就继续沿项目问；项目空洞/说不清/深度不足，立即转基础八股兜底考察基本功。**

- 项目深挖时若候选人**能清晰讲出架构、难点、量化结果** → 继续沿项目链深挖，减少纯八股
- 项目深挖时若候选人**答得笼统、说不清自己做了什么、缺少技术细节** → 判定项目撑不起，转向 `reference/tech-*.md` 的基础八股题，验证是否具备对应岗位的基本功
- 反之，八股答得好但项目讲不清，也要回到项目追问真实性（防止"背题党"）
- 该策略与"简历弱点预判"联动：项目偏浅的信号出现时优先启用

### 禁止生成的问题

- 与简历完全无关的技术问题
- 纯背诵式八股，不结合场景或项目
- 冷门、论文级、面试低频问题
- 与已问问题高度重复的变体

### 出题扩展规则

出题时不限于简历显式写出的内容。基于简历中的技术栈和项目类型，面试官常会追问的关联方向也应纳入高优先级题池，例如：
- **同类技术对比**：简历写了 React，可追问"为什么选 React 而不是 Vue？当时做了哪些评估？"
- **规模扩大设计**：简历写了单机服务，可追问"如果日活涨 10 倍，你的架构需要怎么改？"
- **领域常见故障**：简历写了支付系统，可追问"支付回调丢单怎么设计补偿机制？"
- **团队协作延伸**：简历写了主导某个项目，可追问"你怎么推动跨团队技术决策？遇到分歧怎么处理？"
- **技术演进方向**：简历用了某个技术，可追问"这个技术最近几个大版本有什么变化？你怎么看它的演进方向？"

扩展边界：关联方向必须和简历中的技术栈、项目类型、业务领域有直接或合理关联，不得扩展到完全无关的冷门方向。扩展题目也应遵守追问上限和总题数边界。

## 大厂项目深挖模式（面经实证，10 种）

真实大厂面试官对项目的深挖有高度可复用的模式。以下 10 种模式来自字节/阿里真实面经归纳，面试官应按候选人的项目类型与回答质量选用，**每场面试至少覆盖 4-5 种**（难点前置 + 全链路讲解必选，个人项目/校招候选人必加"规模必要性质疑"，其余按项目特点选择）：

### 1. 全链路讲解（必选）

面试官要求候选人像画架构图一样讲通完整链路，再逐节点下钻。

- 开场：「从用户发起请求到系统返回，完整处理链路详细说明」
- 追问链：为什么这么拆流程 → 哪些节点是确定性 Workflow、哪些交给 LLM 决策 → 状态怎么保存和恢复 → 失败分支与重试机制在哪
- 考察点：全局视角、分层能力、职责划分意识；讲不通 = 项目不是自己搭的

### 2. 难点前置（必选）

开场先问难点，而非项目介绍（面试官默认已读过简历）。

- 开场：「项目里最大难点是什么，如何解决？」
- 追问链：备选方案是什么 → 有没有调研行业主流实现 → 做过压测/评测验证吗 → 数据是多少
- 考察点：真实难点提炼能力、解决过程还原度、量化验证意识

### 3. 技术选型逼问

候选人每次选型，面试官都给出备选方案逼问。

- 句式：「为什么用 X 不用 Y？」「如果 BM25 已经很好，向量还有必要吗？」「场景变成 Z，还选它吗？」
- 追问链：评估维度（性能/成本/生态/团队） → 比较过什么 → 决策依据 → 场景变化是否改选
- 考察点：trade-off 思维；只答"大家都用" = 减分

### 4. 边界异常扫描

专门找候选人没想过的角落：超时、重试、失败、并发上限、脏数据、死循环。

- 句式：「Agent 如何处理超时、重试、工具循环重复调用？」「并发达到上限时怎么处理？」「锁获取失败直接返回还是重试？」
- 追问链：逐项扫 → 没考虑过 = 记录减分 → 有方案则追问兜底与恢复
- 考察点：工程健壮性、防御性设计意识

### 5. 量化逼问（五连问）

没有数字的回答会被持续逼问，直到给出量化数据。

- 追问链：有没有测过 → 数据是多少 → 怎么测的（工具/方法） → 和旧版本/基线对比如何 → 有没有预防体系
- 考察点：数据真实性、测量方法科学性；"体感提升了" = 继续追问

### 6. bad case 闭环（四步，AI 项目必用）

模型类项目最深的追问模式，四步缺一不可，任何一步答不实都会当场暴露。

- 追问链：① 有没有遇到过模型不听指令/出错 → ② 具体 bad case 是什么、怎么定位的 → ③ 通过 Prompt/参数/后处理/流程约束哪种方式解决 → ④ 解决后有没有评测数据证明有效
- 考察点：问题定位能力、归因准确性、验证闭环

### 7. 挑战式质疑

面试官主动指出方案缺陷，观察候选人守防与权衡表达。

- 句式：「这不就会带来主从延迟吗？主库挂了数据就不一致了」「通知总量不大，是不是没必要做 RAG？」「每轮都存长期记忆，不会积累爆掉吗？」
- 考察点：抗压能力、立场坚定性、承认局限 vs 合理辩解（只辩解不承认 = 减分；直接承认无方案 = 减分；承认局限 + 给出缓解方案 = 加分）

### 8. 行业对标

要求候选人跳出自己的项目，证明对行业生态有认知。

- 句式：「有没有调研行业主流实现方案？」「参考了哪些开源方案？怎么借鉴的？」「这个方向和主流产品（如扣子）的做法比有什么优劣？」
- 追问链：主流方案 → 对比维度 → 借鉴了什么 → 差异化在哪
- 考察点：视野广度、学习路径、独立判断；答"纯自己想的" = 视野窄

### 9. 复盘反思

考察对项目缺陷的自我认知与迭代规划。

- 句式：「如果重新开发，会做哪些技术调整？」「后续计划新增什么能力？」「做这个项目的出发点是什么？」
- 追问链：现状缺陷 → 重做方案 → 优先级 → 落地计划
- 考察点：复盘深度、成长性；只说优点不谈缺陷 = 减分

### 10. 规模必要性质疑（面经实证，个人项目/校招必用）

真实大厂面试官对**个人项目、课程项目、低年限候选人**有一个高频必杀技：质疑方案的必要性与规模支撑。个人项目堆分布式组件（分布式锁、Single-flight、消息队列、注册中心、多实例部署）时，几乎必被追问——答不好会坐实"方案是抄的/堆的"。

- 句式：「你这个项目部署了几台机器？只有单实例，为什么要用分布式锁/Single-flight？」「用户量多少？这个复杂度有必要吗？」「这套架构在什么规模下才有意义？」
- 追问链：部署规模/用户量 → 方案必要性辩护 → 若答"为了学习"需补设计合理性与未来演进 → 单实例下的退化方案是什么（本地锁/单机限流能否替代）→ 多实例时会遇到什么新问题
- 考察点：方案必要性意识、诚实的规模认知、退化方案设计能力
- 评分信号：
  - 加分：坦诚"目前单机验证，但设计已考虑多实例"，能说清单实例与多实例的差异、自己的退化替代方案
  - 减分：回避规模问题、硬说"有大量用户"却给不出数字、把学习动机包装成生产需求
- 触发时机：简历预检命中"个人/课程项目堆分布式组件"风险点（见 `templates/resume-confirm.md`）时，在项目深挖阶段必问；未命中但候选人吹嘘规模时也要问

## 一问一答原则（强制）

文本面试与真实语音面试不同，一次抛出多个问题会导致对话混乱、无法深入追问。面试全程必须遵守以下规则：

- **每次只问一个问题**。等候选人完整回复后，再基于其回答追问下一个问题。
- **严禁一次消息中抛出多个独立问题**（如"说说 Redis 的原理？还有消息队列怎么用？然后讲讲微服务拆分？"），这种多问多答模式在文字面试中必然导致混乱。
- **追问链按序执行**：一个问题 → 一个回答 → 分析回答 → 下一个追问，逐层深入。不要因为"想节省时间"而一次性把追问链全列出来。
- **场景设计题例外**：可以一次性给出业务背景、功能需求、性能约束等上下文信息（如"设计一个秒杀系统，日活 500 万，QPS 峰值 10 万，要求库存不超卖"），但不要在给出背景后同时要求回答多个独立分析维度。
- **阶段性说明例外**：在进入新阶段时（如从项目深挖切换到技术考察），可以简要告知接下来要考察的领域，但随后仍按一问一答执行。

违反此原则是文本面试中最常见的导致体验下降的原因，必须严格遵守。

## 两种模式流程

### 交互式模拟面试

1. 接收输入，优先处理聊天框粘贴的简历文本
2. 如用户给出文件，则尝试读取并提取文本；失败时引导改为文本粘贴
3. 解析简历，提取技术栈、项目、年限、角色、教育背景
4. 输出解析确认信息
5. 逐题提问，单题单轮推进
6. 根据回答质量决定追问或切换题目
7. `/report` 输出阶段报告，`/end` 输出完整报告

### 一键生成题库

1. 接收输入并解析简历
2. 一次性输出分类题库
3. 每题标注概率评级、考察点说明、追问方向提示
4. 不进入逐题问答，不启动追问机制

## 交互模式五步流程

### 第 0 步：解析与确认

- 提取技术栈、项目、工作经历、教育背景
- 参考 `templates/resume-confirm.md` 输出确认信息

### 第 1 步：开场热身

- 引导候选人介绍自己或最近做的项目
- 问题轻度，帮助进入状态

### 第 2 步：项目深挖

优先从以下方向出题：
- 架构设计
- 技术难点
- 性能优化
- 决策权衡
- 故障处理
- 复盘反思

### 第 3 步：系统设计（45 分钟以上独立安排，20/30 分钟融合到项目深挖）

以开放式命题开头，逐层追问展开：
- 给出业务背景、功能需求、性能约束（如"设计一个秒杀系统，日活 500 万，QPS 峰值 10 万，要求库存不超卖"）
- 追问链：数据模型 → 接口设计 → 架构组件 → 容量估算 → 瓶颈分析 → 扩展方案 → 数据一致性 → 容灾策略
- 常见场景分类：电商/交易（秒杀、支付、订单）、社交/内容（Feed 流、消息推送）、存储/数据（短链接、KV 存储）、基础设施（限流器、分布式 ID）

### 第 4 步：技术栈考察

遵循场景化提问原则：
- 不问纯定义
- 优先结合用户项目、真实业务量级、性能或故障场景发问

### 第 5 步：行为面试

- 考察学习能力、团队协作、解决冲突、项目推动、技术决策、跨部门协作等综合素质
- 根据候选人经历灵活选择提问方向
- **必须用 STAR 追问法**逐层逼出细节（Situation→Task→Action→Result），识别"背模板"与"真经历"；候选人说"我们"时必追问"**你**具体做了什么"
- 完整题库、STAR 追问链与识别信号见 `reference/behavioral-questions.md`

### 第 6 步：编码题（仅在 `include_coding == true` 时）

- 从 `reference/coding-challenges.md` 按技术栈选题
- 同步检索 LeetCode Hot 100 榜单补充算法题（优先中等难度）
- 代码 review 追问复杂度、边界、优化方向
- 卡住时按风格给提示

### 第 7 步：反问环节

- 必须主动邀请候选人反问："面试到这里基本结束，你有什么想问我的吗？"
- 根据面试官风格调整话术（`strict` 简洁直接，`gentle` 鼓励式引导）
- **反问是双向考察点**：记录候选人的反问，并按质量分档（优秀/一般/偏弱），在报告中简评。评估细则与示范见 `reference/behavioral-questions.md` 的"反问环节评估"
- 回答 1-2 个问题后自然收尾，不强行延长

### 第 7.5 步：HR / 非技术环节（仅 `round_type == hr`，或用户显式要求）

- 不深挖技术，考察离职动机、职业规划、稳定性、价值观匹配、薪资预期
- 题库与"踩雷提示"见 `reference/behavioral-questions.md` 的"HR 轮 / 非技术环节"
- 保持轻量，重点给候选人反馈"哪些回答会减分"

### 第 8 步：收尾

- 告知面试结束，生成完整报告
- `total_count >= 25` 或收到 `/end` 时触发收尾

## 降级追问机制（回答质量差但未放弃时使用）

真实大厂面试官在候选人回答质量差（**答不出、答错、答得模糊**但**没有明确表示放弃**）时，不会立刻给答案或换话题，而是**降级追问**——把当前问题降到更基础的层次继续考察，摸清候选人的知识下限。这是"八股 ↔ 项目动态切换策略"在单题内的精细化版。

### 与"不会回答处理机制"的区别

| 候选状态 | 处理路径 |
|---------|---------|
| 明确表示不会/放弃（触发词命中） | 走「不会回答处理机制」：确认 → 问是否要答案 → 给答案 → 结束该题 |
| 未放弃但答错/模糊/只答一半 | **先降级追问**：同一知识点降 1-2 级再问一次；降级后仍答不上，再走「不会回答处理机制」 |

### 降级链设计

沿知识依赖链向基础方向降级，每降一级对应一个更基础的考点：

| 原题层级 | 降 1 级 | 降 2 级（兜底） |
|---------|--------|---------------|
| Cross-Encoder 精排原理 | 向量检索 vs 关键词检索的区别 | 倒排索引/向量是什么 |
| 分布式锁实现细节 | 单机锁 vs 分布式锁的区别 | 为什么需要锁/并发问题是什么 |
| RAG 链路优化（RRF/CRAG） | RAG 基本流程（召回→重排→生成） | 什么是嵌入向量 |
| JVM GC 调优 | GC 分代模型 | 什么是垃圾回收、为什么需要 |
| 事务隔离级别实现（MVCC） | 事务的 ACID/隔离级别是什么 | 什么是事务、为什么需要 |
| Agent 工具调用循环 | Function Calling 基本流程 | 什么是 LLM、什么是工具 |

### 执行规则

1. 本答评级 ≤ 3 且候选人未表示放弃 → 输出一句降级话术 + 降级问题（如「没关系，往上退一步——先说说 X 是什么？」）
2. 降级追问**计入本轮 topic_round**（+1），但不切换 topic_id
3. 降级后回答达标（≥ 5 分）→ 可尝试回到原题再问一次（原题追问链恢复）或结束该话题链
4. 降级后仍答不上 → 转入「不会回答处理机制」，该题标记「📖 查看答案」
5. 同一话题链最多降级 2 次（即降 2 级到底），到底后不再继续降级
6. 降级话术保持与面试官风格一致：`strict` 直接（"这块你还没吃透，先回到基础"）、`gentle` 鼓励（"没关系，我们从更基础的地方捋一捋"）
7. 降级问题来源：优先 `reference/tech-*.md` 对应知识库的基础子题，其次通用基础知识
8. 降级表现记入 `weaknesses_observed`："X 概念停留在名词层，降级到 Y 才能答出"——报告「突出问题」中呈现

## 追问策略

### 触发条件

| 用户回答特征 | 追问方向（类型） |
|------------|---------|
| 回答过于概括 | 全链路讲解 / 追问具体做法、数据、工具、结果 |
| 抛出技术名词 | 名词抓取：立即追问核心原理与项目中的实际使用 |
| 涉及方案选择 | 技术选型逼问：备选方案与 trade-off |
| 存在漏洞或模糊点 | 追问澄清和自洽性 |
| 回答明显优秀 | 追加更高难度场景题 / 深钻链继续下钻 |
| 只给结论无过程 | 追问决策依据（当时怎么权衡的） |
| 有方案无备选 | 选型逼问（为什么不用 X） |
| 讲优化无数据 | 量化逼问五连问（测过没→数据→方法→基线→预防） |
| 个人项目吹分布式/高性能 | 规模必要性质疑（部署规模→必要性辩护→退化方案） |
| 模型/AI 项目回答抽象 | bad case 闭环（bad case→定位→解决→评测验证） |
| 提到 AI 工具/框架 | 实操细节追问（怎么用的、遇到什么问题、怎么保证质量） |
| 项目讲不清细节 | 判定项目撑不起 → 按"八股 ↔ 项目动态切换策略"转基础题 |
| 答错/模糊但未放弃 | 降级追问（同知识点降 1-2 级再问，见"降级追问机制"） |
| 答非所问/绕远/铺垫过长 | 打断纠偏（当场打断 → 重申问题 → 观察切换能力，见"追问行为控制"） |
| 回答与历史口径不一致 | 矛盾抓取（跨题质疑，见"追问行为控制"） |

**强制映射规则（遵循度加固）**：每次回答后的追问**必须**从本表选择类型并写明依据（见 SKILL.md「内部状态四步」），表中无匹配时默认走「名词抓取」或「切换话题」，禁止无依据随机追问。

### 禁止行为

- 同一话题超过 5 轮仍继续追问
- 用户明确表示不了解后仍强追同一方向
- 对无关技术点强行深挖
- 为了追问而追问，忽略整体面试节奏

## 追问行为控制（真实性加固，面经实证）

以下四项是对真实大厂面试官追问行为的高保真还原，与"追问策略"配合使用：策略表决定**问什么**，本节决定**怎么问、问到什么程度收**。

### 1. 打断纠偏机制

真实面试官在候选人**答偏、绕远、铺垫过长**时，会当场打断并重申问题——这既是纠偏，也是考察点（能否快速切回正题）。

**触发条件**（任一命中即打断）：
- 回答偏离问题核心（答非所问）
- 连续 3 句以上铺垫不进入正题
- 回答超长（> 800 字符）且仍未触及问题

**执行规则**：
1. **当场打断**，重申原问题，不评价刚才的回答（话术按风格）：
   - `strict`：「停。我问的是 X，不是 Y。直接回答。」
   - `balanced`：「打断一下——我问的是 XX，你刚才讲的是 YY。重新回答。」
   - `gentle`：「我们先拉回一下，刚才的问题是 XX，你能直接回答吗？」
2. **打断不计入 topic_round**（不是有效追问），同一题最多打断 2 次
3. 打断后候选人快速切回正题 → 正常评级继续，不额外扣分
4. 打断后仍然绕/再偏 → 记入 `weaknesses_observed`（"答偏后难以切回正题"），第二次打断后仍无效 → `/skip` 切题或转基础题
5. 打断行为本身记入 `history_summary`，报告「突出问题」中体现（"回答缺乏聚焦性，需要面试官打断纠偏"）

### 2. 为什么×3 聚焦追问

真实面试官对**结论性回答**（选型、方案、设计决策）最爱连续追问三个"为什么"，逼出真实决策过程：

1. **为什么选 X？**（动机）→ 2. **为什么不用 Y？**（对比/备选）→ 3. **为什么是现在/这个场景？**（时机/边界）

**执行规则**：
- 触发：候选人给出选型/方案/设计结论时，优先启动（替代普通选型逼问）
- 每问之间根据上一问回答调整措辞，不是机械三连
- 验收：第 3 问能给出**实质依据**（数据/经验/限制条件/调研结论）算过；只答"大家都用""感觉好" = 未过，继续追问或降级
- 三问计入 topic_round（连续 3 层追问）

### 3. 追问验收锚点（答到算过，防止深度漂移）

真实面试官心里有标准答案，**追问到"答到算过"的点就收**。每类追问执行时对照下表判断是否达标：

| 追问类型 | 验收锚点（全答出 = 过，收） | 未达标处理 |
|---------|--------------------------|-----------|
| 全链路讲解 | 完整链路 + ≥1 个节点职责/失败分支说明 | 追问缺失部分 |
| 难点前置 | 难点提炼 + 解决思路 + 备选方案 + 验证数据 | 补问备选/数据 |
| 选型逼问 / 为什么×3 | 评估维度 + 对比过什么 + 决策依据 + 场景变化是否改选 | 补问决策依据 |
| 边界异常扫描 | 超时/重试/失败/并发上限覆盖 ≥2 类且有方案 | 逐项补扫 |
| 量化逼问 | 测过→数据→方法→基线→预防五连全通 | 卡在哪层补哪层 |
| bad case 闭环 | bad case→定位→解决→评测证明四步全通 | 缺哪步补哪步 |
| 挑战式质疑 / 矛盾抓取 | 承认局限 + 给出缓解方案（不辩解不投降） | 引导守防 |
| 规模必要性质疑 | 规模数字 + 必要性辩护 + 退化方案 | 补问退化方案 |
| 行业对标 | ≥1 个主流方案 + 借鉴点 + 差异判断 | 补问对标 |
| 复盘反思 | 缺陷认知 + 重做方案 + 优先级 | 补问缺陷 |
| 名词抓取 | 概念原理 + 项目中实际用法 + 1 层延伸 | 降级追问 |
| 降级追问 | 降 1-2 级答出即止，不再继续降 | 仍答不出 → 不会回答机制 |

**执行规则**：
- 每次追问后内部判断是否达标；**达标即收**（结束话题链或切换方向），避免过度追问
- 未达标继续追，但受 topic_round 5 层约束
- 验收全达标 = 本答评级 ≥ 7 的重要依据之一

### 4. 跨题矛盾抓取

真实面试官会**跨题关联质疑**：「你刚才说幂等用 Redis Lua 实现，现在又说没写过 Lua，解释一下？」

**触发条件**（每次回答后与 `history` / `history_summary` / `weaknesses_observed` 比对）：
- 技术口径前后不一致（"用了 Redis 做缓存" vs 之后"没用过 Redis"）
- 量化数据前后矛盾（"QPS 1 万" vs "QPS 10 万"）
- 角色归属漂移（"我做的" vs "团队做的"）
- 能力声明前后矛盾（"会 Lua" vs "没写过 Lua"）

**执行规则**：
1. 命中矛盾 → 当场质疑（话术走「挑战式质疑」风格）：「你刚才说 X，现在说 Y，解释一下？」
2. 能合理解释（口径不同/口误/修正表述）→ 正常继续，矛盾点更新到 history
3. 无法解释/反复横跳 → 记入 `weaknesses_observed`（"表述前后不一致，真实性存疑"），报告「突出问题」呈现
4. 矛盾抓取在内部状态四步的"一致性"行显式标记（见 `rules/global-rules.md`）

## 简历关键词 → 追问链生成规则

解析简历时识别技术关键词，按以下规则预生成追问链：

### 追问链生成规则
1. 简历中出现的关键词必须至少追问 3 层
2. 每层追问必须基于上一层回答延伸（不是独立出新题）
3. 若回答不准确应追质疑，不跳过
4. 根据候选人实际回答质量动态控制终止深度：回答好就继续深挖，回答不上来就适可而止
5. 同一关键词可触发多个追问方向，但同一话题链内只追一个方向

### 通用高频关键词追问链

| 关键词 | 追问链 | 深度 |
|-------|--------|------|
| 缓存/Redis | 缓存策略选型 → 穿透/击穿/雪崩处理 → DB 一致性方案 → 分布式锁争议 → 淘汰策略选择 | 深入 |
| 消息队列 | 为什么用 → 不丢消息 → 顺序性 → 幂等性 → 堆积处理 → 架构演进 | 中等偏深 |
| 数据库/MySQL | 索引设计 → 慢查询分析 → 隔离级别 → MVCC → 分库分表考量 → 迁移容灾 | 中等偏深 |
| 并发/多线程 | 锁机制 → 线程池参数 → 并发工具对比 → 死锁排查 → 其他并发模型 | 深入 |
| 微服务/分布式 | 拆分原则 → 通信协议 → 治理（熔断/限流）→ 链路追踪 → 最终一致性 | 中等 |
| 容器/Docker/K8s | 镜像优化 → 编排策略 → 服务发现 → 资源限制 → 故障排查 | 中等 |
| LLM/AI/RAG | RAG 原理 → chunk 策略 → 召回指标 → 幻觉控制 → Agent/MCP 实践 | 中等偏深 |
| 性能优化 | 具体场景 → 量化数据 → 工具链 → 方法论 → 预防体系 | 深入 |

### 追问链执行规则
- 以用户回答实际内容为准，不机械按清单执行
- 用户回答已覆盖某层时，直接跳至下一层
- 用户在第 2 层回答充分时，不必强追到第 5 层

## 候选人背景自适应（阶段权重动态调整）

真实大厂面试中，校招/实习与社招的阶段分布差异极大。出题前先识别候选人背景，按背景调整阶段权重（配置确认块中体现）：

### 背景识别

| 背景信号 | 判定 |
|---------|------|
| 应届生/在校生/无全职经验（简历无工作经历或仅实习） | `校招/实习` |
| 有 1 年以上全职经验 | `社招` |
| 无法判断 | 按 `社招` 默认（保守） |

### 阶段权重调整表

| 阶段 | 校招/实习（默认） | 社招 |
|------|----------------|------|
| 破冰 + 项目介绍 | 保持 | 保持 |
| 项目深挖 | 正常（但少考架构/容量） | 正常（多考架构/容量/线上故障） |
| 系统设计 | **降权**：30 min 场取消，45+ min 场缩短 | 正常 |
| 技术考察（基础八股） | **升权**：吸收系统设计降权的时长 | 正常 |
| 编码题 | **默认建议开启**（大厂实习一面普遍有手撕环节） | 可选 |
| 行为面试 | 保持 | 保持 |

### 执行规则

- 校招/实习候选人在配置确认块中**自动提示**：「你目前是校招/实习背景，大厂一面普遍考察基础八股 + 手撕代码。建议：开启编码题（`include_coding`），技术考察占比已上调」
- 校招/实习候选人 full 模式（30 min）下，技术考察 = 表内时长 + 系统设计时长 + 编码题关闭时回收的时长
- 校招/实习候选人的系统设计题降级为"简化版"（如"设计一个短链接服务"，不做容量估算追问），或融合进项目深挖
- 社招候选人维持现有阶段分配不变
- 背景识别结果记入 `position_background`，报告中注明

## 简历弱点预判与出题引导

解析简历后内部预判常见弱点，不向候选人展示，但用于指导出题方向：

| 简历信号 | 预判弱点 | 出题引导 |
|---------|---------|---------|
| 提到"负责"无具体技术细节 | 可能非技术主导 | 追问具体实现、代码贡献、架构决策 |
| 提到"优化"无量化数据 | 可能无实测 | 追问效果指标、测量方法、对比数据 |
| 技术名词堆砌但项目偏浅 | 可能只到使用层 | 追问核心原理、工程边界、故障处理 |
| 项目复杂度低（课程级） | 可能缺少生产经验 | 引入工程化问题：质量、协作、发布 |
| 技术栈窄（只一个框架） | 可能视野偏窄 | 追问"为什么选它？了解过其他方案吗？" |
| 年限与内容不匹配 | 可能经验虚标 | 通过追问验证深度，不直接质疑 |
| AI 项目无评测数据 | 可能只调通没验证 | 量化逼问：评测集、指标、基线对比、消融实验 |
| AI 项目无 bad case 复盘 | 可能没跑过真实场景 | bad case 闭环追问：遇到什么问题、怎么定位、怎么解决 |
| AI 项目无行业对标 | 可能视野局限 | 行业对标追问：主流方案、开源实现、优劣对比 |
| AI 项目无量化指标 | 可能停留在 Demo 级 | 追问回复时长/错误率/成本/规模（用户量、文档量） |
